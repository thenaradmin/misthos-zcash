§ 01Keys

Each key lifts one line.

Every employee is paid from their own child wallet. The employer's export-proof gives an employee that wallet's full viewing key, so the key reads that employee's line and nothing else in the run.

Checked on testnet. Alice's key sees her funding note and her payout, and nothing in Bob's payout. The tests also check, with real keys and real note encryption, that a key sees only its own output in a shared funding transaction.

A key is forever. An employee's key shows all of their payouts from this employer, past and future. There is no revocation. The treasury's own viewing key is never exported.

§ 02Blocks

Two steps, 11 and 19 blocks apart.

A child wallet per employee is what makes a one-line proof possible. It adds a hop, so payouts wait a random number of blocks after funding instead of landing right behind it.

Step 1 · funding

One transaction from the treasury

It sends each employee's pay plus 0.0001 ZEC to that employee's child wallet. The extra covers the payout fee.

Delay

Random block waits

Drawn from the OS RNG (default 2 to 6 blocks per step) and written to each child's ledger before any waiting, so a restart never redraws them.

Step 2 · payout

Each child wallet pays its employee

One note in, one output, no change. A rerun with the same label skips anyone already funded or paid.

Honest limit: on a quiet testnet, a funding transaction followed by N shielded payouts within a few blocks can still be linked by timing alone. The delays shrink that signal; they don't remove it.

§ 03Proof

Show one line to a lender.

The employer signs every payout with ed25519. The employer exports one employee's signed proof from the CLI and hands it over; the employee's lender checks it against the chain, not against a screenshot.

  • The employer signs the network, the payout txid, the child wallet, the amount in zatoshis and the pay period.
  • The employer exports one proof for one employee: those fields, the signature and that employee's child wallet viewing key. Nobody else's.
  • The lender runs verify-proof --lwd. It checks the signer against the published employer key, fetches the mined transaction from lightwalletd, decrypts it with the key and checks the signed amount.

On the recorded run, verify-proof --lwd accepted each employee's proof and rejected:

  • the other employee's txid
  • the funding txid
  • a changed amount
  • a changed period
  • a changed signature
  • a different employer key
§ 04Deductions

What the bars don't cover.

  • Testnet only. Mainnet addresses and a mainnet network setting are refused in code.
  • Timing. Funding and payouts can still be linked by when they land, as above. Payouts also go in roster order.
  • Keys can't be revoked. A shared employee key keeps reading that employee's payouts from this employer.
  • One extra transaction per employee per run, for the funding hop that makes per-employee proofs possible.
  • Lightwalletd learns a little. pay --two-step asks it directly for the funding txid, which tells its operator which IP cares about that txid.
  • Not built: NEAR Intents, the zakura-one-time-ivk crate, ZIP 311 payment disclosures (still a draft). Transactions are built by zingo-cli.
  • The desk can't pay. Payouts and proofs run only from the CLI; the dashboard's pay and proof endpoints answer 410 Gone.

The desk does not pay. A one-click payout straight from the treasury could not be proven per employee, so payouts run only from the CLI with pay --two-step.

Pay and prove

from a terminal
  1. Pay through per-employee child wallets, with random block delays between funding and payouts.
    payroll pay roster.csv --two-step --label oct-2026
  2. Export one employee's employer-signed proof. There is no download here: it had no login.
    payroll export-proof roster.csv --employee <id> --label oct-2026
  3. The employee's lender checks the signature and the chain.
    payroll verify-proof proof.txt <txid> --lwd https://<testnet lightwalletd>:443
